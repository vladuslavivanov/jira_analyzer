# Спецификация требований

# Введение

**Назначение**

Данный документ описывает функциональные и нефункциональные требования к ИИ-агенту, предназначенному для автоматизированного аудита качества проектных задач в Jira.

**Область действия**

Продукт представляет собой MVP-версию веб\-сервиса на языке Python, который интегрируется с Jira для анализа описаний задач и формирования аналитических отчетов.

**Определения и сокращения**

* **DoD (Definition of Done):** Критерии готовности задачи.  
* **JQL (Jira Query Language):** Язык запросов Jira.  
* **LLM (Large Language Model):** Генеративный ИИ для семантического анализа текста.  
* **MVP:** Минимально жизнеспособный продукт.

# Общее описание

## Бизнес-потребность

Некачественное описание задач (отсутствие декомпозиции, DoD, неясные формулировки) замедляет разработку, а ручной аудит тысяч тикетов невозможен для проектного офиса.

## Видение продукта

Инструмент автоматически получает данные из Jira, использует LLM для оценки по критериям качества и агрегирует статистику для руководителей.

## Характеристики пользователей

Топ-менеджеры, менеджеры проектов (PM) и тимлиды.

### User Story

**Руководитель проектного офиса:**

* Как руководитель проектного офиса, я хочу получать сводные отчеты по всем проектам дивизиона, чтобы масштабировать контроль качества на множество команд и выявлять системные проблемы в дисциплине ведения задач.  
* Как руководитель, я хочу видеть "красные флаги" по задачам, которые не обновлялись более N дней ("зомби-задачи"), чтобы вовремя реагировать на блокировки в разработке.

**Проектный менеджер:**

* Как PM, я хочу автоматически проверять наличие Definition of Done (DoD) и качество декомпозиции Эпиков, чтобы не допустить поступления в работу плохо описанных задач.  
* Как PM, я хочу получать результат анализа в формате Markdown или таблицы, чтобы быстро локализовать проблему и предоставить исполнителю конкретные замечания по исправлению.

**Тимлид:**

* Как тимлид, я хочу исправлять постановку задач в тикетах как можно раньше, чтобы мои разработчики понимали постановку задачи, когда приступают к её выполнению.

## Основные ограничения

Работа только с **Jira**, реализация на **Python**, развертывание строго во **внутреннем контуре** компании.

# Функциональные требования

### Пользовательские сценарии

Система должна поддерживать работу следующих пользовательских сценариев.

**Сценарий №1. “Базовый экспресс-аудит”**

* **Предусловие:** Приложение развернуто во внутреннем контуре, настроены доступы к Jira API и ключи LLM-провайдера (например, DeepSeek).  
* **Акторы:** Менеджер проекта, Тимлид.  
* **Поток действий:**  
  1. Пользователь открывает веб\-страницу инструмента.  
  2. Пользователь вводит конкретный идентификатор (ID) задачи Jira.  
  3. Система запрашивает данные задачи через API и передает их LLM для анализа.  
  4. ИИ проводит семантический анализ Description, наличия DoD и качества формулировок.  
  5. Система выводит на экран результат анализа с оценкой и списком замечаний.  
* **Альтернативные действия:**  
  1. 3а. Некорректный ID или отсутствие прав доступа: Система уведомляет об ошибке и предлагает проверить ID.  
* **Результат:** Визуализированная оценка качества задачи в веб\-интерфейсе

**Сценарий №2. “Продвинутый групповой анализ”**

* **Предусловие:** Пользователь подготовил критерии выборки (ID родительской задачи или JQL-запрос) и описание задачи анализа с указанием критериев оценки.  
* **Акторы:** Проектный офис, PM.  
* **Поток действий:**  
  * Пользователь в веб\-интерфейсе указывает критерий выбора группы задач (например, JQL или Parent ID).  
  * Пользователь настраивает фильтрацию (например, "не проверять закрытые тикеты").  
  * Пользователь указывает промпт с описанием задачи анализа с подробным описанием критериев оценки.  
  * Система сохраняет результат анализа в персистентном хранилище и генерирует отчет.  
  * Пользователь выбирает желаемый формат отчета (Markdown, JSON или файл таблицы) для экспорта.  
* **Альтернативные действия:**  
  * 4а. Превышение лимитов API LLM: Система выстраивает очередь запросов для обеспечения стабильной обработки массива данных.  
* **Результат:** Структурированный сводный отчет для последующего исследования.

**Сценарий №3. “Базовый анализ датасета задач”**

* **Предусловие:** Пользователь подготовил датасет с набором задач для анлиза и описание задачи анализа с указанием критериев оценки.  
* **Акторы:** Проектный офис, PM.  
* **Поток действий:**  
  * Пользователь в веб\-интерфейсе указывает файл с данным задач для анализа.  
  * Пользователь указывает промпт с описанием задачи анализа с подробным описанием критериев оценки.  
  * Пользователь запрашивает анализ задач  
  * Система запускает асинхронную многопоточную обработку всей группы задач.  
  * Система сохраняет результат анализа в персистентном хранилище и генерирует отчет.  
  * Пользователь выбирает желаемый формат отчета (Markdown, JSON или файл таблицы) для экспорта.  
* **Альтернативные действия:**  
  * 4а. Превышение лимитов API LLM: Система выстраивает очередь запросов для обеспечения стабильной обработки массива данных.  
* **Результат:** Структурированный сводный отчет для последующего исследования.

### Перечень требований

* **FR-1: Интеграция с Jira API \[Must\].**  
  Система должна подключаться к Jira через API для выгрузки данных о задачах, их связях и истории изменений.  
* **FR-2: Анализ содержания (Description) \[Must\].**   
  Автоматическая проверка описания задачи на наличие обязательных атрибутов и соответствие указанным пользователем критериям.   
* **FR-3: Оценка по критериям \[Must\].**   
  Для анализа текстового описания задач на соответствие критериям качества нужно использовать LLM. Итоговый результат оценки должен быть выражен в виде численной метрики.  
  Предлагается система оценивания критерия:  
1. бинарная оценка: 0/1  
2. 5-бальная система: 0-5  
3. проценты: 0-100%

* **FR-4: Формирование отчетов \[Must\].**  
  Составление итоговых отчетов в формате **Markdown** с результатами аудита всех задач по имеющимся в момент формирования отчета в хранилище результатам анализа отдельных задач.  
  Формат отчета:  
* Сводная таблица с оценками критериев каждой выбранной задачи.  
* Среднее значения оценки по каждому критерию.  
* Описание критериев оценивания.  
* Детали анализа для каждой задачи:  
  * Идентификатор задачи, название  
  * Опциональное общее описание  
  * Таблица с деталями оценки для каждого критерия:  
    * название критерия  
    * оценка  
    * описание проблемы  
    * рекомендация к исправлению  
* Опциональное полное описание задачи из таск-трекера

* **FR-5: Конфигурация через внешние файлы \[Must\].**  
  Системные и шаблонные промпты и правила оценки (критерии) должны быть вынесены в отдельные файлы (.md или .json) для редактирования их отдельными средставами.  
* **FR-6: Выборка по JQL/ID \[Сould\].**  
  Возможность указывать анализируемые группы задач через JQL-запросы, идентификаторы задач (ID) или ID родительской задачи (Epic).  
* **FR-7: Графический интерфейс (Web UI) \[Should\].**   
  Наличие веб\-интерфейса для ввода параметров поиска, раздел для настройки критериев и описания задания (промпта)  для анализа, раздел для визуализации результатов анализа.  
* **FR-8: Персистентное хранение \[Should\].**   
  Сохранение результатов анализа в базе данных.  
* **FR-9: Фильтрация по статусам \[Should\].**   
  Система не должна проверять закрытые задачи без явного запроса пользователя.  
* **FR-10: Анализ динамики («Зомби-задачи») \[Could\].**  
   Выявление задач, находящихся в одном статусе без обновлений более N дней.  
* **FR-12: Многопоточность и асинхронность \[Should\].**  
  Реализация очереди запросов к LLM для одновременной обработки массива задач.  
* **FR-13: Управление режимо раздельного анализа \[Should\]**  
  Пользовательский интерфейс должен предоставлять возможность включить режим анализа задач по каждому критерию в отдельности.

# Нефункциональные требования

* **NFR-1: Точность оценки \[Must\].**   
  Система должна обеспечивать точность оценки по разработанным критериям критериям качества не ниже **90%**.  
* **NFR-2: Безопасность данных \[Must\].**  
   Хранение и использование ключей API (например, DeepSeek) должно осуществляться через защищенные конфигурации.  
* **NFR-3: Производительность \[Should\].**   
  Асинхронная работа с API LLM должна сократить время ожидания при аудите группы из более чем 10 задач.  
* **NFR-4: Вертикальная масштабируемость \[Should\].**   
  Архитектура должна позволять масштабировать аудит на десятков тысяч задач для нужд всего проектного офиса.  
* **NFR-5: Горизонтальная масштабируемость \[Would not\]**  
  Архитектура не рассчитывается на высокий уровень входной нагрузки. Одновременно запросы в систему может отправлять до 10 пользователей.

# Требования к интерфейсам

## Интерфейс пользователя

Веб-страница с полями ввода JQL/ID и кнопкой запуска анализа, а также областью отображения Markdown-отчета.

На странице должны располагаться 

* поля ввода для подключения к таск-трекеру (URL и персональный токен),  
* виджет для загрузки датасета с задачами,  
* раздел с настройкой промпта для LLM: системный промпт, описание задачи анализа с настройкой отдельных критериев,  
* результат анализа должен отображаться на той же странице, с которой был запущен анализ, только Markdown отчет.

## Программные интерфейсы

Взаимодействие с Jira через стандартные библиотеки (Atlassian Jira API) и с LLM-провайдером через REST API.
